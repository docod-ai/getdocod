# DOCOD internals: how everything works, down to the bit

This is the maintainer's document. The README sells and orients; this explains the machinery. Read it before arguing about the design in an issue, because most "why not X?" questions have an answer that lives here.

## 0. The one sentence

DOCOD is a set of contracts (markdown + YAML) interpreted by three small programs: an installer (bash), a runtime (node), and a dev validator (python). All state is derived from files on every run. Nothing maintains an index by hand, and nothing trusts an agent's claim when a machine can check it.

## 1. The four layers, and what enforces them

| Layer | Lives in | Contains | Changes when |
|---|---|---|---|
| 1. Method | `spec/method.yaml` | stages (define/orchestrate/confirm/observe/redefine), 12 capabilities, skill registry, status machine, who_approves, approval schema | the method itself evolves |
| 2. Contract | `spec/agent.yaml`, `spec/artifacts.yaml`, `spec/commands.yaml`, `spec/rules.yaml`, `agents/*.md`, `rules/*.md`, `spec/skills/*` | what every agent and artifact IS | agents/artifacts evolve |
| 3. Adapter | `adapters/*.yaml` | tool names, materialization, enforcement wiring per harness | a harness changes |
| 4. Instance | `docod.yaml` (user's project root) | language, docsRoot, topology, targets | per project |

Neutrality is not aspirational, it is checked: `validate-layers.py` (dev-only, never installed) greps layers 1 and 2 for vendor names, tool names and stack terms against curated lists, with documented exclusions for false-positive words. Every check in it was tested by planting the error first. The recurring failure this project made nine-plus times, and the validator exists to kill, is: a reference declared in prose with nobody on the other side and no validator watching. Whenever you add a cross-reference between files, ask who validates it.

Key vocabulary invariants (never translate, never rename casually): agent keys, artifact keys (including the Portuguese-born `evidencias`), action names, capability names, status values `draft|review|approved`, verdict values, diagnostic severity keys `critical|high|medium|low` (the report data block is machine-readable: keys map to colours, display labels localize, keys do not — a pt-BR `crítica` once fell through the colour map in silence), postcondition prefixes `deterministic:|evidence:|judgment:`, placeholders `{docsRoot} {ws} {seq} {slug} {date} {version} {target.tasksRoot} {target.path} {target}`, the marker `QUESTIONS FOR THE USER:`, and the marker `generated-by: docod`.

## 2. Anatomy of an agent (`agents/<key>.md`)

One file, two halves.

**Frontmatter = the contract** (parsed by runtime and validator):

```yaml
key: frd                     # identity; must be unique
interactive: true            # needs answers from a human
capabilities: [...]          # abstract needs; adapter maps to tools
skills: [...]                # must exist in method.yaml registry, both directions checked
contract:
  owns: { artifact: frd }    # one artifact, one owner (validator checks both directions)
  triggers: [...]            # advisory: who this agent typically activates
  actions:
    create_frd:
      stage: define
      scope: [project, ws]
      requires:              # PRECONDITIONS, evaluated mechanically by status
        - artifact: prd
          status: [approved]
          waivable: false    # waivable: true blocks softly; waiver recorded in frontmatter
      reads: [...]           # every key must exist in artifacts.yaml (validated)
      writes: { artifact: frd, status: draft }   # agents may only write draft/review
      postconditions:
        - "deterministic: ..."   # machine-checkable; verify covers the computable subset
        - "evidence: ..."        # agent must show command + output
        - "judgment: ..."        # not enforceable; gated by reviewers
```

**Body = the role**, in prose, with exactly three enumerated role sections, each opening a block after a `---` line: `## structure` (the document template it delivers), `## inquiry` (what it asks, with the conventions "NEVER skip.", "Ask closed:", "Skip if:", "Cost of the error:", "### On closing"), `## style`. The validator parses roles as "the `## x` heading that opens a block after `---`"; a fourth section name is an error. `interactive: true` without `## inquiry` is an error (promises to ask, doesn't say what).

Every reverse_* action (and `extract_from_code`) additionally honors the `reverse_conventions` block in `spec/agent.yaml`: mandatory triangulation of legacy docs (cited as external provenance, never imported), numbered DIV-nn divergences — CLAIM-vs-REALITY, where the claim side is a legacy doc or another code artifact's stated contract — plus numbered RISK-nn one-way findings (code + the judgment that it is dangerous: PII, destructive actions, exposure; same evidence bar, owner per item), and three question classes never mixed (gap, product decision, external-owner — the last always lands in the single `external-questions` queue, which `status` chases). The `diagnostic_mode` block defines the reverses running UNHOOKED from governance (no approvals, pins or gates; everything snapshot; pre-read, never pre-approved) — packaged as `/docod:diagnose`, consolidated by the tech-lead into the `diagnostic` artifact. Three more field-learned blocks in `spec/agent.yaml` bind every producer: `write_order` (stamp `status` LAST — its absence IS the incomplete-run marker, so an interruption cannot pass silently), `reference_discipline` (reference by content and declare in `inputs[]`; file:line evidence carries the observed fragment in backticks on the same line — position AND content, so displacement is provable; naked anchors warn in live documents, snapshot records never warn but their anchors are still re-read and tallied as-of-now; a prose-quoted hash either belongs in `inputs[]` or not in the text) and `divergence_taxonomy` (a FALSE CLAIM is a divergence and justifies an amendment; an UNMET TARGET is the normal condition of a PRD/SLO and justifies nothing — reviewers classify before proposing). Current census: 28 agents. 27 producers plus `tech-lead` (owns the append-only `counsel` log and the `diagnostic`; materialized TWICE since 1.13.0 — the conversational half (sparring, counsel, `guide`) in the main session as `/docod:lead`, because sparring is conversation and cannot bounce through a hand-back protocol, and the producer half as the RESTRICTED subagent `docod-tech-lead`, `consolidate_diagnostic` only, because a producer with no wrapper left `/docod:diagnose` delegating to a target that did not exist — and, since 1.8.0, the resident guide to the method itself: its `guide` action derives the real state and answers a lost user with next step + why in method terms + the exact command, never running the step; expertise is READ from spec and status on every run, never recited, because a memorized flow rots the day the runtime changes). Identity tests that killed or converted agents in v1: delivers a document (agent) vs. delivers a craft (skill: 13 of them) vs. is a discipline someone obeys (rule: 4 templates specialized by `rules-factory`).

## 3. The artifact registry (`spec/artifacts.yaml`)

Every artifact has: `stage` (metadata, never a folder), `owner` (validator checks the owner agrees), `scope` subset of `[project, ws, target]`, and a `path` template per scope. 42 artifacts (the 38th: `external-questions`, the single append-only queue of questions only an outside owner can close — one file on purpose, unlike the per-agent `decisions` logs, because the queue's value is being ONE list to chase; the 39th: `diagnostic`, the dated, immutable consolidation of a diagnostic-mode run — DIV and RISK registers with owners, provenance census, honest coverage; the 40th and 41st, 1.16.0: `bands`, the machine-read control-band contract the slos speak to humans about, and `observation`, the dated snapshot record where a band violation lands — machine evidence verbatim, owner judgment, human re-entry; the 42nd, 1.17.0: `evals`, the agent-configuration regression suite — owned by qa-executor precisely because rules-factory must not own the check that judges its own changes, with `### EV-nn` ids that never vanish and rules amendments shipping the suite's measured run as evidence).

Path resolution is the load-bearing trick. Templates use placeholders; the runtime resolves `{docsRoot}` from the instance (default `docs/`), `{ws}` from context, and produces **one pattern per target**, substituting `{target.tasksRoot}`, `{target.path}` and `{target}` (the target's key) per entry in the instance's `targets:`. All remaining placeholders (`{seq}`, `{slug}`, `{date}`, `{version}`, and `{ws}` when unbound) become `*` and the result is globbed. Unbound `{ws}` deliberately globs instead of vanishing: an unregistered front's artifact must show up as a finding. The glob engine is home-grown (about 30 lines) because `fs.globSync` only exists from node 22 and node 18 is the floor.

Filesystem layout is by NATURE, never by stage (a revisited document must not change homes): `product/ design/ decisions/ quality/ ops/ releases/ standards/ workstreams/` under `{docsRoot}`; target-scoped artifacts (tasks, evidence, qa, codereview) live next to the code under `{target.tasksRoot}`.

**Ownership exceptions** (exactly two, both narrow and declared as `co_writer`): the `task` file (executor may tick `- [x]` checkboxes, add inline evidence and stamp `execution.started` before its first edit, may NOT touch scope/criteria/tests, because an executor that edits its own bar self-approves through the back door) and `workstreams.yaml` (the user closes fronts via the `ws` command; only `prd` creates them).

**Lineage classes** (born from the first real test):

- default (live): `inputs[].hash` mismatch means stale, verify fails it.
- `lineage: snapshot` on the nine record artifacts (design-review, impact-analysis, codereview, qa, evidencias, postmortem, adr, release-notes, counsel): inputs are observed-at, reported but never failed, because refreshing them would lie about what was analyzed.
- inputs pointing at an `append_only` artifact (the `decisions` sidecar): observed state of a file that grows by design, not live-checked.
- input entries may carry `external: true` (imported .docx provenance): recorded, not resolvable. An unregistered input WITHOUT `external` is still a failure; that is how typos get caught.
- input entries may carry `lineage: snapshot` (EDGE-level, 1.10.0): the relation to one input is not always the artifact's relation to all of them — security-design vs data-design is live (model changes ⇒ threat model may be wrong), but the api-contract derives FROM the security-design, so a contract change asks for another look, not invalidation. One artifact-level value forced a false choice, and the field workaround (dropping the input, citing in prose) erased machine-readable provenance. Edge snapshot keeps the relation written and the alarm honest: observed-at, never failed, revisited by impact-analysis. Downgrade only — inside a snapshot artifact every edge is observed-at regardless (`lineage: live` there is ignored with a warning), and rebless never re-pins an observed-at edge.

## 4. Hashes, approval, and the status machine

`sha256Body(file)` hashes the content EXCLUDING the frontmatter, truncated to `sha256:` + 16 hex chars. Excluding frontmatter is essential: writing the approval into the file must not invalidate the approval it records. The frontmatter delimiter is ANCHORED (`fmClose()`, shared by every split in the runtime, mirrored by the validator's `FM_DELIM`): the closer is a line that is exactly `---`, never the first `---` substring — an unanchored search once closed the frontmatter at a `# ----` comment rule inside it, and everything below (a diagnostic's whole `report:` block, in the field) silently became body while verify stayed green.

Human gate: `docod.mjs approve <file> --by <who>` writes `approval: {by, at, content_hash}` and sets `status: approved`. **Effective status** is computed on every read: `approved` with no approval record shows as `approved?`; `approved` whose `content_hash` no longer matches shows as `review` with the warning "INVALID approval, content changed after the approve by X on Y". Nobody remembers anything; the hash remembers. Downstream `requires` re-block automatically because they consult effective status, not written status.

Re-approving changed content prints the previous approver/date and a ready `git log -p --since=... -- <file>` line: the unread made visible, never forced (a mandatory checkbox is theater). And re-approving AMENDED content is mechanical about the radius: it requires `--impact <impact-file>` (recorded in the frontmatter) or `--no-impact "<reason>"` (a recorded waiver) — touched doc means mapped radius. Cosmetic bulk goes through rebless. And since 1.19.0 the gate is GRADUATED: every approval records an ENVELOPE — a structural fingerprint of what it blessed (section count, heading-structure hash, the explicit ID inventory, the inputs[] set, a hash per protected section — the spine, declared per artifact in the registry by ordinal, language-neutral) — and `approve --correction --reason` re-approves a factual, no-semantic-change edit by CONFIRMATION instead of re-review. The machine delimits the class, never the author: outside the envelope the refusal NAMES the broken leg (the `p95 100→300ms` one-character flip lives in a protected spine and takes the full ceremony; a vanished RF id is named; a renamed heading refuses) and inside it the confirmation is still a recorded human act, with every downstream live pin on the previous hash re-pinned automatically — the radius executed instead of waived. The fingerprint exists because the approval never kept the text it blessed, only its hash: the envelope is what makes "compare against the approved version" computable without a VCS.

The producer's stamp (1.22.0): the final stamp of a COMPLETE run is `review` ("complete, awaiting the gate"); `draft` is the producer's own declaration of incompleteness, with a `draft_reason`. The contracts' `writes: {status: draft}` is the status a document is born with, never the one it is delivered with — the runtime does not read that field; it is doctrine. A read is not a transition: the report derives and never writes, so no viewer moves a draft to review by opening it. `approve` on a draft records `from_status: draft` (surfaced by the EXCEPTION STREAM) and explains what draft means instead of lecturing about the flow — a finished document stamped draft is the producer's slip, not the human's.

Review ROUNDS (1.22.0): `codereview`, `qa` and `bugs` are sequential and registered `rounds: true` — records of ONE verdict, unlike an adr, where each sequential file is its own decision. Only the newest round per folder counts for gates and debt; earlier rounds are history, kept on disk, marked by status and verify (which also names the round and whether it counts). The codereview's upstream-smells opposition runs against the latest qa round.

Agent gates (design-review, qa, code-review): the verdict lives in the REVIEWER's artifact frontmatter (`verdict: approved|approved_with_comments|changes_requested|rejected|blocked`); the owner moves their own status, legally only when a fresh `approved` — or, since 1.19.0, `approved_with_comments` — verdict is newer than their last edit (comparable via hashes). A with-comments verdict satisfies gates WITH the comments as DERIVED declared debt: status surfaces every standing one on every run, nobody maintains a list, and the field's "vai e vem" (a one-cell fix re-paying the full ceremony plus a waiver) is retired. Three reviewers, three objects: document before code, diff, behavior. None reviews its own work; none moves anyone's status.

## 5. The runtime (`docod.mjs`)

Plain node >= 18, ESM, zero installation: js-yaml is vendored in `vendor/js-yaml.mjs` (MIT, license alongside), pinned to the YAML 1.2 CORE schema. The pin matters: the default 1.1 schema converts `2026-07-17` into a Date object and reserialization would mutate the user's file. The runtime neither lies nor "improves" what it read.

Commands (each derives everything fresh from disk):

- `status [--ws]`: workstreams from `{docsRoot}workstreams.yaml`, artifact instances via glob, effective status per file, orphan ws folders reported as findings, open entries of the `external-questions` queue surfaced on every run (a question with an owner outside the room must cost something to ignore; a queue that does not PARSE reports as possible LOSS, never as an empty list — in the field a corrupted queue once rendered as "zero open questions" with eight entries gone), then `possible now` vs `blocked (and why)` computed by evaluating every action's `requires` against the effective statuses present. Two derived blocks ride along, nobody maintains either: DECLARED DEBT (1.19.0 — every standing `approved_with_comments` verdict; it satisfies gates, the comments remain owed) and the EXCEPTION STREAM (1.21.0 — every standing exception the method has granted, in one place: correction approvals, approvals taken `from_status: draft`, partial `rebless_scope` sweeps, `impact_waived` reasons, waived preconditions via the canonical `waived_requires` shape or any legacy frontmatter key containing 'waiv', and — when the bundle repo is the cwd — the dev-side third-party name grants; the standing records ARE the list, and the block is the review board's agenda: the machine assembles the evidence, the human makes the call). Contract: NEVER lie; a status that reassures is worse than none.
- `start`: entry doors given what exists; refuses to be a start if artifacts exist (that is `continue`).
- `continue <ws>`: focused status.
- `approve`, `ws list|add|done|abandon --reason` (abandon without reason is refused: a front that vanishes silently is lost work with no record). `ws add` is the LIGHT registration door, born from the field: a front whose tasks already existed would have cost a prd round to restate a report — the method absorbed its own legitimate bypass. `--reason` is mandatory and stored in the registry entry (`registered_by: ws add`, `registered_reason`); the prd remains the default door.
- `question add|answer` (1.13.0): the SINGLE WRITER of the `external-questions` queue — born from the field loss where three parallel reverses rewrote the file, the YAML stopped parsing and eight entries vanished. `add` allocates the next EQ-nn and appends under an O_EXCL lockfile (concurrent adds raced the allocation; a stale lock refuses with the recipe, never auto-removed) in candidate→parse→assert→write order — a corrupted queue REFUSES the write, because appending over corruption buries the evidence. `answer` flips the entry surgically and preserves every other byte (the field file carries its loss report as YAML comments; a redump would erase the forensics). The command is an instruction, not a lock — detection in `verify` carries the guarantee.
- `observe [--record]` (1.16.0): OBSERVE closing in execution. Evaluates the `bands` contract against the instance-produced metric snapshots in `{docsRoot}ops/metrics/` — everything derived FRESH per run (rolling baseline from the windowed snapshots, latest point excluded, n>=5 or declared insufficient; detection is the state). Every check prints its numbers; a stale latest snapshot is OBSERVING BLIND, a declared-but-unmeasured metric is a finding, an unparseable band is a config error — nothing is skipped silently. `--record` materializes the dated `observation` draft (machine half verbatim, judgment sections as declared gaps for `assess_observation`); re-entry through prd/ws/impact-analysis stays a human act. Exit code non-zero on violations or config errors, so CI can gate on it.
- `verify <file>`: EXTERNAL verification of the computable class, run by the caller, never the producer. Checks: frontmatter parses (real parser, not grep), status in enum, approval hash vs current content, every `inputs[].hash` against live source artifacts (honoring the lineage classes above), artifact registered — and COMPLETENESS, added after the field case where a truncated FRD (11 requirements and 4 sections short, its promised `frd.yaml` never written) passed with VERIFY OK and a hundred ✓, which made the command's name a lie. Three truncation detectors, all fail-tier: section COUNT vs the contract's declared minimum (count, not names — documents are written in the instance's language and matching English names would false-fail, and a false positive trains the user to ignore the alert; a declared `Title` rides in the H1 and is discounted), kept frontmatter promises (a frontmatter naming a companion file that does not exist fails; `inputs[]`, `approval` and `template` are excluded), and presence of `status` on registered artifacts (the producer stamps status LAST per `write_order`; its absence IS the incomplete-run marker). Warn tier (`⚠`, does not fail): a hash field holding a non-hash value; a prose-quoted hash matching no current artifact and no declared input (one survived three rounds and an approval while wrong — nothing watched it); NAKED file:line anchors in live-lineage documents (a bare anchor rots on any edit of the cited file; an anchor accompanied by the observed fragment in backticks on the same line carries its own displacement proof and passes — the reverse's evidence discipline REQUIRES file:line, and a guard firing on the method's own prescribed output would be defect #3 reborn; snapshot records never warn but their anchors ARE re-read and tallied as an as-of-now observation — a fresh snapshot with a fragment off its line is mis-transcription, an old one is measured drift, and the dossier's "anchors verified" count must be a number the machine checked); an undeclared ADR link — except a document citing ITSELF (the ADR's own number, which its `## structure` requires in the title) and except append-only logs like `counsel`, whose function is citing ADRs: an alert that fires on every instance by construction trains the reader to skip the line where a real problem will one day be. And COVERAGE, on the `tasks` index: every ID defined upstream (definition-shaped lines in system-design/frd) must be cited by at least one task file, or verify warns — born from the auth hole (a component named "Identidade & Autorização" whose extracted tasks built its nouns and lost its verb; every gate passed because every gate checks its artifact against its INPUT, and no gate checked the input was carried forward — this is the external witness for that invariant; migration.yaml `coverage-invariants` tracks the sibling edges). And THE QUEUE CHECKS (1.13.0), on `external-questions` only — before them, verify ran exactly two checks on a .yaml artifact (parses + registered), both green over a queue that had lost eight entries: duplicate ids fail; a sequence gap fails NAMING the missing id, checked PER PREFIX FAMILY, because the field file carries two id grammars (EQ-nn canonical, EXT-nnn grandfathered — renumbering breaks the documents that cite them) and an EQ-only check would have passed green over the exact entries the field lost; state outside `open|answered` fails; legacy field names (`raised_by`/`blocks`) are read via alias and warned, never failed — those are precisely the restored entries. And THE DECLARED-LINKS FAMILY (1.21.0), three checks in one release: the TRACEABILITY INVARIANT on the system-design — set equality between each component's `Traces to:` lines and the transposed traceability table, vocabulary declared in the owner's `## structure` (`Traces to:` never translated; cells `·`-separated; an id inside a parenthesis is a mention, not an assignment), reporting DIFFERENCES (which id, which side) and never a bare count, because the four-times-improvised throwaway version of this exact check once matched by accident and hid the only real divergence — both sides present and disagreeing fails, half the vocabulary warns; the SCENARIO FLOOR on the frd — warn per RF whose definition block carries no criterion under the never-translate `Acceptance criteria:` label (a requirement with no scenario is acceptance nobody can check; warn, never fail at birth, legacy frds predate the vocabulary); and the ENFORCEMENT EDGE — an adr's optional frontmatter `enforced_by: [EV-nn]` names the evals case that holds the decision up, and a DECLARED edge is a checked edge: dangling fails, retired fails (a retired check enforces nothing), unparseable fails, while the reverse direction is the case's own `Origin:` line and continuous execution is the adapters' merge_gate point. Every pass is explained ("observed-at, not live-checked"), because a silent pass teaches nothing.
- `rebless --by <who> --reason "..." [--repin-inputs] [--yes]`: the cascade-cost answer. Batch re-approval of invalid approvals plus opt-in re-pinning of stale live-lineage inputs. Guards: reason mandatory and stored inside every touched approval (`rebless_reason`); without `--yes` it prints the plan with a per-file diff command; re-pin resolves the source by the input's `key` (both sides normalized: extension off, path relative, parenthesized scope-prefixed keys unwrapped; path-first, basename after) and acts only on a UNIQUE resolution — snapshot, append-only and external inputs are never touched. What it CANNOT resolve it now says out loud: every stale input with no unique resolution is listed under `CANNOT RESOLVE` with the reason (no current instance / key does not single out N candidates) and the exit code goes non-zero — "I don't know how" is an answer, never a silence. And `--only <path>` (repeatable) scopes the sweep — born from the field's 128-re-pin pointer tax: the scope filters which files are touched AND which orphans are reported (an out-of-scope orphan is the next sweep's problem), and the plan header names the scope so the record shows the sweep was partial. The prior behavior ("nothing to rebless" over unresolvable stale inputs) was a silent failure in the worst direction a tool can fail: a stale input walked out looking whole. Verify also warns on undeclared links: a body citing ADR-nnnn absent from `inputs[]`. And on attribution mismatch: a `codereview` whose `upstream_smells` list names a BUG the sibling qa classified `local` — two judgments with opposite biases, opposed mechanically; the disagreement is the alarm.
- `report`: collects the same derived state plus document bodies and task checkbox progress (`- [x]` vs `- [ ]` gives the kanban lane: todo/doing/done), injects JSON into `report-template.html` (with `<` escaped so no document can close the script block), writes static, offline, self-contained `report.html`. UI labels localize via an `I18N` dict keyed by the instance `language:` with English fallback. Cards show a red `changed since approval` chip when body hash diverges from the recorded approval. `report --diagnostic` is the sellable twin: it renders `diagnostic-template.html` from the `report:` data block the tech-lead's `consolidate_diagnostic` emits — a shock-first, evidence-dense dossier (file:line with the observed fragment, the census read recorded-vs-ratified, the `pre-read not pre-approved` line kept) — the diagnostic deliverable.

## 6. The installer (`install.sh`)

Pure bash, zero dependencies, idempotent, merge-safe. The merge rule in one line: everything of ours lives namespaced (`docod`), and what is not ours we never touch. A new installation selects its adapter with `--adapter claude-code|codex|agents-1`; after that, the preserved `docod.yaml` is authoritative. A conflicting explicit flag is refused instead of silently changing harness semantics. When the user explicitly changes that field, the next install retires only generated surfaces from the previous harness; user-owned namesakes survive.

What every adapter gets: (1) the bundle copied into `.docod/` (excluding dev-only files, installer packages, tests, generated reports and the user's `docod.yaml`); (2) an instance `docod.yaml` created once and never overwritten, with warnings for older shapes; (3) canonical skills in `.agents/docod/skills/`; (4) detection-based migrations — no state file, detection is the state; (5) a root discovery block in `AGENTS.md`, with `CLAUDE.md` kept as the Claude-compatible entry point; and (6) a Node availability check that warns without failing.

The selected adapter then materializes the harness surface. Claude Code receives skill links in `.claude/skills/`, native agents in `.claude/agents/` and ten command files in `.claude/commands/docod/`. Codex receives repository-scoped skill links in `.agents/skills/`, native custom-agent TOML files in `.codex/agents/`, and a command-router skill backed by the contracts in `.docod/adapter-assets/codex/commands/`. Codex descriptions are shortened by complete words, never byte slices; every TOML is written to a temporary path, strictly validated as UTF-8 without relying on the process locale, and only then published. The neutral `agents-1` profile receives only the portable skill links and root instructions. In every case a namesake without `generated-by: docod` is skipped, never clobbered.

The generated subagent is a thin envelope: its first instruction is to read `.docod/agents/<key>.md` in full (subagents do not expand `@` references, so the read is an instruction; a copy would be scheduled drift). The envelope carries eight non-negotiable harness rules, notably: run `status` first and stop on blocked requires; never write `approved`; computed hashes only, never placeholders; product answers go to the `decisions` log while technical decisions get flagged for the `adr` agent; write everything in the instance's `language:` (the method speaks English, the product speaks the instance); run `verify` for the computable class; and the interactive hand-back: a subagent cannot reach the user, so it stops and returns `QUESTIONS FOR THE USER:` instead of inventing.

`/docod:run <agent> [action] [ws]` is the explicit door: it delegates, relays hand-back questions verbatim, treats a reply with neither a written artifact nor questions as a FAILED run (junk detection, learned from a real junk return), runs `verify` on the delivery, and never approves.

## 7. Materialization on Claude Code (`adapters/claude-code.yaml`)

Mode: subagent, with owned costs stated in the adapter: (1) interactive degrades to the hand-back protocol; (2) hooks do NOT fire inside subagents (anthropics/claude-code#34692, #33049; open issues, current behavior, not a promise), so `deterministic` enforcement is in-band for everyone plus the external `verify`; (3) the model may auto-invoke a subagent; each description says "invoke ONLY when the user explicitly asks", an instruction, not a lock, accepted risk. External tools (Context7, Playwright) are declared `external: true` with `degraded_to` and install hints; a missing tool degrades honestly ("NOT VERIFIED"), it never pretends. Swapping the adapter file swaps the harness; layers 1-2 do not move.

## 8. Materialization on Codex (`adapters/codex.yaml`)

Mode: custom agent plus repository skill. Each neutral producer becomes a thin `.codex/agents/docod-<key>.toml` envelope that reads the canonical role from `.docod/agents/<key>.md`; hyphens become underscores only in Codex's agent identifier. Interactive work uses the same explicit `QUESTIONS FOR THE USER:` hand-back, the parent session performs external verification, and the tech lead remains restricted to `consolidate_diagnostic` as a subagent.

Since 1.18.0 every adapter also carries a `coercion:` section, the regulated profile: six shared enforcement points (approval gate, hook integrity, supply chain, sandbox/egress, merge gate, config regression) that the method OWNS as points and each deployment binds to whatever its harness actually offers. Cooperation stays the method (layers 1-2 do not move; a gate that coerces is an orchestrator in disguise); coercion is a deployment option. Claude Code binds several points to managed settings; Codex marks what depends on surface and workspace policy as `runtime_defined`; the neutral adapter says out loud that a file spec coerces nothing. Every point degrades honestly to the same vendor-neutral floor: branch protection, required review, and the runtime's exit codes (`verify`, `observe`, the validator) as required CI checks, a floor that lives outside every harness and therefore holds for all of them.

The public command contract does not change with the harness: `/docod:status`, `/docod:start`, `/docod:continue`, `/docod:approve`, `/docod:ws`, `/docod:report`, `/docod:run`, `/docod:lead`, `/docod:loop`, and `/docod:diagnose`. The repository root is the distributable package (`.codex-plugin/plugin.json`), so the setup skill can reach the version-matched installer; its command skills live in `skills/`. Plugin name `docod` plus one explicitly invoked skill per command preserves the namespace natively. A repository installed without the plugin gets the same exact syntax through the `docod-commands` router skill and root `AGENTS.md` instructions. This is deliberate: Codex custom prompts have their own `/prompts:<name>` namespace, so DOCOD does not model its stable API as custom prompts.

`validate-layers.py` checks that declared adapter roots and command contracts have an installer materialization, and that every Codex command contract has a plugin skill with implicit invocation disabled. `tests/install-adapters.sh` exercises clean install, user-owned collision preservation, idempotent reinstall and adapter mismatch refusal for all three profiles.

## 10. The design principles that explain everything else

1. Derived, never maintained: all state is recomputed from files; an index would drift by tomorrow.
2. Never lie, never reassure: invalid approvals show red; gaps show as gaps; passes are explained.
3. One artifact, one owner; exceptions are named, narrow, and written down.
4. The human orchestrates: commands inform and record; a command that decides is an orchestrator in disguise. Counsel (tech-lead) recommends and logs; it never invokes, approves, or edits.
5. What a machine can check, a machine checks, and never the machine that did the work.
6. References need validators: every cross-file reference either has a check or it is a bug waiting for its third occurrence.
7. The method speaks English; the product speaks the instance's language.
8. False positives are worse than gaps: they train the user to ignore the alert.
9. Guards tighten without loosening: a resolver may learn to recognize an identified source; it never learns to guess an ambiguous one.
10. The machine automates the work and leaves the judgment where it belongs: rebless executes in bulk, but whether a change was cosmetic is, and remains, the human's call.
11. Make the implicit sayable before making it enforceable. The answer to patch-divergence was never more enforcement: it was giving the root-cause a field, the smell a list, and the disagreement a name — once a judgment is structured and recorded, opposition becomes computable and the alarm rings itself. Vocabulary first; mechanism follows.
